# Handoff: installable app (PWA)

- **Manifest** (`src/manifest.webmanifest`): Eclipse Realms, `id: /eclipse-realms`, `start_url: /play`, standalone + window-controls-overlay, orientation any, theme/background `#0a0a0f`, 7 `any` + 2 maskable icons, 4 shortcuts (Play, Character, Forge → /forge/runes, Sanctum). **No screenshots yet**: add real narrow/wide captures of /play later.
- **start_url /play**: the town is the main entry; it is CSR-only, so offline it boots from the precached `/index.csr.html` shell.
- **iOS**: apple meta tags, status bar `black` (/play doesn't pad safe-area-top), 15 portrait startup images in `assets/brand/splash/`.
- **Install offer** (`shared/pwa/pwa.model.ts`, rule + spec): second session OR first craft, 25 s dwell, cookie banner answered, not standalone; dismiss cooldown 14 → 30 → 90 days, then never. iOS gets Share → Add to Home Screen. Never on /play. Device-local key `godforge-install-offer` (not game state). Analytics: `pwa_install`, `pwa_launch`.
- **App chrome** (`app-chrome.component.ts`): offline pill (pointer-events none; the gateway's own `online` listener does the sync), WCO title-bar strip, `html.gf-play-route` (no overscroll, canvas touch-action none), warms /play chunk + art in standalone. Both pieces load lazily via `pwa-outlet.component.ts` (initial bundle is at its hard budget).
- **Service worker v3**: precaches the shell plus its hashed bundles atomically, along with fonts, the Seamworks bg and `/offline.html`. Offline navigation order: cached page → shell → offline.html. `isExpectedType` now also guards pages.
- **Stale-build recovery** (error-tracking + boot-recovery): it no longer purges caches while offline. It probes with a HEAD to /robots.txt, because `navigator.onLine` lied under test.
- **Update flow ("A new version is ready — Reload")**: an installed app or long-open tab never navigates, so before this it ran an old bundle for days. Now:
  - *Stamp* — `scripts/stamp-build-id.js` (in `postbuild`, so `npm run build`; a bare `npx ng build` is unstamped and the feature stays off until you run the script) hashes the hashed bundle names `index.csr.html` references into a 12-hex build id, writes `/version.json` `{build}`, puts `<meta name="gf-build">` after the charset in every app page, and replaces `BUILD_ID` in `service-worker.js`. Before this the worker was byte-identical across deploys, so `registration.update()` could never find anything. Identical source gives an identical id (no false prompts).
  - *Detect* — `shared/pwa/app-update.service.ts` (lazy chunk via `<app-pwa-outlet kind="update">`, every route incl. /play): on start, every 30 min while visible, on visibility→visible (≥2 min apart) and on `online`: `registration.update()` plus `fetch('/version.json', {cache:'no-store'})` against the document's meta. Either signal suffices (`updateVerdict` in `app-update.model.ts`). A worker waiting while the page already runs the served build is activated quietly (no prompt, no reload). Works without a service worker too (version file only), which is how local e2e runs.
  - *Worker* — install no longer calls `skipWaiting()`: an update waits for the toast (or for every tab to close). Cache names (`VERSION`) are NOT per deploy, so an old tab's lazy chunks are never deleted under it. `{type:'GET_BUILD'}` on a MessageChannel answers the worker's build.
  - *Toast* — `update-toast.component.ts`, top-centre (below `--nav-h` off /play, under safe-area/title-bar on /play), then steps down below any visible control in its band (`placeClear`, re-run every 1.5 s, so the in-progress /play phone HUD redesign is followed, not hard-coded; capped to the top 40%). Not shown at all while busy: any rendered `[aria-modal="true"]` (station panels, dialogs), the HUD enemy bar `.meter.enemy`, or any `[data-gf-busy]` (opt-in hook for new surfaces). Later = dismissed for that build id, per tab session. EN + ES via `app-update.i18n.ts`.
  - *Reload* — `GameStateGateway.settleForReload()` flushes every save owner synchronously (localStorage settled first), gives the cloud push ≤2.5 s, then `SKIP_WAITING` to the waiting (or ≤6 s still-installing) worker, reload once on `controllerchange` (4 s fallback). With no worker it just reloads: navigations are network-first, so it lands on the new deploy anyway. Never automatic.
  - `firebase.json` serves `/version.json` `no-cache`. Tests: `app-update.service.spec.ts` (fake registration), `e2e/play-update.spec.ts` (deploy simulated with `page.route`: version.json and every document carry a new id; sells at the Vendor while the toast waits, Reload inside the ledger's write throttle, the sale survives; 375px no-overlap check).
- Local builds use `environment.ts` (`production: false`), so the SW never registers locally. To test, register it by hand.

## Human checks
- Android Chrome: install appears after the second session, installs, launches /play, shortcuts work, airplane-mode relaunch.
- iOS Safari: instructions card, Add to Home Screen, splash, status bar, offline relaunch.
- Desktop Chrome: install, title-bar overlay toggle (nav not under the controls, window draggable).
- Offline pill shows and sync resumes on reconnect when signed in.
- Update toast after a real deploy: installed Android app left open shows it within 30 min or on refocus; Reload keeps the last action. **iOS standalone is unverified**: WebKit's `updatefound`/`controllerchange` in home-screen apps is not proven here; the version-file path plus a plain reload is the fallback there.
